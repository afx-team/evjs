# plugin-authoring

Demonstrates the typed evjs plugin factory together with ordinary build-time
lifecycle hooks.

- **`definePlugin()`** — declare one stable, short `id` for every plugin-owned surface and return an installable factory
- **`pluginOptions()`** — declare independent, type-safe Application and Page contracts
- **`plugins: [metadataPlugin(config)]`** — install and configure the Application in one expression
- **`page.config.ts#plugins.metadata`** — configure a Page with the same plugin `id` and no plugin import
- **`src/plugin-types.d.ts`** — generated by evjs as a stable bridge to the static `ev.config.ts` type for Page editor types
- **`setup`** — read the resolved Application setting before graph analysis
- **`contribute`** — iterate only enabled, typed Page settings
- **`configure`** — update framework config before defaults are resolved
- **`configureBundler`** — modify the underlying bundler config (type-safe via `utoopack()` helper)
- **`beforeBuild`** — run after fresh bundler facts, before canonical output is linked
- **`afterBuild`** — run after canonical output is published
- **`transformHtml`** — modify the parsed HTML document after asset injection with current HTML context

For plugins that need to declare generated `.ev` artifacts and attach them to
framework slots, see the generated contributions documentation.

Application and Page settings do not merge with each other. Within either
contract, authored fields are deeply merged over that contract's defaults
before validation. Because this example installs `metadataPlugin()` normally
and declares Page defaults, omitting `metadata` uses those defaults. A Page may
use `metadata: false` to disable the plugin or an object to override the
defaults; `metadata: true` selects the defaults explicitly.

The application itself uses the unified Core 0.3 model:
`src/pages/page.tsx` defines `/`, `src/pages/layout.tsx` supplies the SPA root
layout, `ev.config.ts` installs both factories, and `src/pages/page.config.ts`
configures Page behavior. Route and Document effects, when needed, are derived
from enabled Pages by plugin contributions rather than configured through
separate owner bags. Page plugin settings are build-time graph values and are
not automatically serialized into browser runtime.

## Run

```bash
npm run dev
```

## What to look for

1. The resolved Application metadata value in `setup`
2. The enabled, typed Page metadata values in `contribute`
3. Console output from `beforeBuild` and `afterBuild` hooks during build
4. The `<!-- Built with evjs | file.html | N asset(s) -->` comment in the output HTML (injected by `transformHtml`)
5. The type-safe `.txt` rule declaration in the `configureBundler` hook
